## What was built

Two owners, two lifetimes — deliberately, not one uniform rule:

- **Read-only handlers keep the thread-local handle** they already had. It is
  bounded by the worker-thread pool and released at shutdown. Measured: 4 open
  handles after 40 concurrent HTTP reads across 4 threads, 0 after shutdown.
- **`POST /v1/images/{id}/reviews` and `GET /v1/exports/reviews` get the
  request-scoped provider.** These are the two paths that can leave a
  transaction behind, so `request_connection()` releases the connection in a
  `finally` — the next request on that thread can never inherit it.

New surface, all inside the task's allowed change surface:

| Symbol | Where | What it guarantees |
|---|---|---|
| `release_conn() -> bool` | `app.py` | this thread's handle is rolled back and closed |
| `open_connection_count() -> int` | `app.py` | the open-handle count is observable, not asserted |
| `close_all_connections() -> int` | `app.py` | shutdown releases every handle this process opened |
| `request_connection()` | `app.py` | the scoped provider; nestable, exception-transparent |
| `_lifespan` | `app.py` | FastAPI lifespan wiring, so the release actually runs |
| `db.initialize(conn, db_path)` | `db.py` | migrations once per **database** per process, under a lock, never cached on failure |
| `db.close(conn)` | `db.py` | roll back then close; idempotent; a rollback failure is printed, not hidden |

`get_conn()` and `set_conn()` keep their signatures and their existing
thread-local / injected-fixture semantics. `run_migrations()` is untouched, so
the F002 fixture and every existing caller keep working.

## Two things a reviewer should push on

1. **The read/write split is a judgement call, not a measurement.** Read-only
   handlers still hold one connection per worker thread until shutdown. That is
   bounded and released, and it is the pre-existing design, so F007 did not
   rewrite it. Wrapping the remaining handlers in `request_connection()` is now
   a one-line change each if the integrator wants per-request reads too.
2. **The migration memo is keyed by resolved path.** If the database *file* is
   swapped underneath a running process, the first query fails loudly
   (`OperationalError: no such table: …`, swept and recorded) instead of
   self-healing the way the old per-thread re-run sometimes did. Loud beats
   silent, but it is a behaviour change and it should be a conscious one.
