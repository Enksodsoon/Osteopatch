## 1. Why this task exists

The old `api.ts` had one failure mode for everything: `HTTP ${status}`. A 409 conflict, a 500
server fault, and a socket that died mid-save were indistinguishable to a reviewer — and the
message for a dropped connection during a save was actively misleading, because it implied
nothing had been recorded when the write may well have committed.

`apiErrors.ts` is the new single source of truth:

| Symbol | Purpose |
|---|---|
| `ApiError` | `status: number\|null`, `code`, `message`, `request_id?`, `outcome: "rejected"\|"unknown"`, plus legacy `detail` and `conflict` |
| `decodeBody` | Parses a body **at most once**; returns `null` for empty/non-JSON instead of throwing |
| `classifyError` | Turns a thrown `fetch` value into a typed error, abort vs network aware |
| `safeDetail` | Redacts tokens, signed URLs, absolute server paths, and stack traces |
| `isRetryable` | Mutations are **never** retried; auth failures are **never** retried |
| `codeForStatus` | 401/403/404/409/422/429/5xx → distinct semantic codes |

`api.ts` keeps every existing export and signature. Every added parameter is optional, so no call
site in `App.tsx`, `Workbench.tsx`, `ReviewPanel.tsx` or the enterprise client needed editing —
and none of those integration-owned files were touched.

## 2. The three-outcome contract

| Situation | `status` | `code` | `outcome` | What the reviewer may be told |
|---|---|---|---|---|
| Server said no (409/422/…) | real number | mapped | `rejected` | "Reload and try again" |
| Server error (500) | real number | `server_error` | `rejected` | "Nothing was saved" |
| User navigated away | `null` | `aborted` | `rejected` | nothing — it is not an error |
| Socket died during a **write** | `null` | `network` | **`unknown`** | "may or may not have been recorded — reload first" |

The last row is the whole point. `ApiError.mayHaveCommitted` is true exactly when `outcome` is
`unknown`, and no code path is permitted to label that "unsaved".

## 4. Task steps 7 and 8

**Step 7 — stale responses.** A deferred-promise test resolves response **B before A** and asserts
the resolution order, so the client never forces an ordering the UI then has to undo. Each request
also increments a monotonic counter exposed as `api.lastRequestId()`, giving a component enough
identity to drop a stale reply without comparing payloads.

**Step 8 — no host hard-coding.** All URLs remain relative `/v1/...`; the Vite proxy and
`VITE_API_TARGET` are untouched. No second API provider was introduced.

## 6. Defects found in this task's own code

1. **Self-import in `apiErrors.ts`** — `export { ApiError as ApiErrorClass } from "./apiErrors"`
   made the module import itself. Vitest tolerated it; `node` refused with `ERR_MODULE_NOT_FOUND`.
   Removed. Found only by running the sweep outside the test harness.
2. **Stray CR at EOF in `api.ts`** — the file held 248 CR against 247 LF, so the task's own
   `git diff --check` exited **2** flagging every line as trailing whitespace. Normalised.
3. **Dead import** — `isRetryable` was imported into `api.ts` but only re-exported; the
   TypeScript build gate caught it (`TS6133`). Removed from the import list.
4. **`status` regression (completion check)** — `submitReview` hardcoded `status: 200`, but the
   backend answers **201** for a newly created event and **200** for an idempotent replay
   (`app.py:407`). The pre-F004 client reported the real status, so this was a regression that
   would have quietly broken R006's retry reconciliation. Fixed by adding `request<T>()` returning
   `{status, data, request_id}`, with `fetchJson` layered on top; `submitReview` now reports
   `result.status`. Locked by three new tests.

Each was fixed at the cause. No lint suppression and no weakened assertion.

## 9. Limitations

- No component consumes `outcome`/`mayHaveCommitted` yet. Rendering "may or may not have been
  recorded" in `ReviewPanel.tsx` is not in this task's 3-file surface; `App.tsx` and
  `ReviewPanel.tsx` are integration-owned and were deliberately left untouched. The signal exists
  and is tested, but the UI does not yet display it.
- The client was exercised at the unit layer against a stubbed `fetch`, and end to end by the
  browser E2E suite. Task step 11's literal rehearsal — disconnecting a live test API and showing
  a recoverable message in the UI — remains **NOT_RUN** in a browser.
- `api.lastRequestId()` provides identity but no component consumes it yet; wiring it into
  `Workbench.tsx` belongs to U001/R003.
- Enterprise's own `api.ts` was read as a pattern reference but is **not** migrated; it still
  throws plain `Error` with stringified JSON. That is E001–E003 territory.
