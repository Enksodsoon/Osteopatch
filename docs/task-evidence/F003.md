## What was actually wrong

Step 01 traced every existing filter before anything was edited
(`scratch/task/f003-step01-trace.md`). Two defects, both **latent** — the real
store has exactly one model bundle and one project, so neither is observable on
today's data, and both go live the moment a second bundle exists:

1. **The gallery ranked across tenants.** `list_images` called
   `_priority_rank_map(conn)` with no `project_id`; `get_image` called
   `_priority_rank_map(conn, project_id)`. The same image therefore got
   different rank numbers depending on which endpoint a tenant read, and the
   gallery's numbering counted other tenants' rows — exactly the "unauthorized
   existence inferable from ranks" failure Step 08 names.
2. **There was no model-scoped selection at all.** `model_bundle_hash` appeared
   in the SELECT list and in the output dict and in **no WHERE clause**, while
   the join was `LEFT JOIN prediction p ON p.image_id = s.image_id`. Prediction
   identity is `(image_id, model_bundle_hash)`, so a second bundle silently
   produced a second gallery card and an inflated `total`.

## What was built

`app/g6/backend/osteopatch/scope.py` (new) owns one question — *given a
verified request, which rows may this caller see?* — and answers it once:

- `ScopeContext`, frozen, with `project_id`, `dataset_version_id`,
  `model_bundle_hash`, `deployment_allowlist`, `review_session_id`, `actor_id`,
  plus a `cache_key` that covers all of them.
- `resolve_prediction_rows(conn, scope) -> list[SelectedPredictionRow]`, which
  intersects project ∩ dataset ∩ allowlist ∩ model **in SQL**, so `total`, ranks
  and pages cannot describe a wider set than the caller may read.
- The pre-D001 dataset version is `legacy-ingestion-manifest:sha256:7151385…`,
  derived from the verified immutable manifest, whose `image_id` column is its
  membership — never a filename guess, and never "unrestricted" if unreadable.
- A duplicate `(image_id, model_bundle_hash)` raises
  `PredictionSelectionIntegrityError` rather than choosing a row.

`queries.py` now routes gallery, detail, rank, search and export through that one
selection. `review_proxy.py` resolves the scope server-side. No route, schema or
frontend file changed.

## Two things a reviewer should push on

1. **`MODE_PROJECT_ONLY`.** The pre-F003 `project_id=` argument still works and
   applies project + model + allowlist but *no dataset version*, because
   `test_project_isolation.py` builds a synthetic corpus that is deliberately not
   in the manifest and is outside this task's boundary to change. On the real
   corpus the difference is nil (manifest membership == store membership, measured
   1,144/1,144), and `scope_for_request` — the server-side entry point the
   enterprise proxy uses — always declares a dataset version. It is a named,
   documented mode, not a silent fallback, but it is a real surface and retiring
   it is a judgement the integrator should make rather than inherit.
2. **Model-scoped review state.** The `revision` token stays image-global on
   purpose (`repo.submit_review` compares against the image-global maximum, so a
   model-scoped revision would cause spurious 409s), while the *status* only
   counts events referencing the selected `prediction_id`. Full history is still
   returned.
